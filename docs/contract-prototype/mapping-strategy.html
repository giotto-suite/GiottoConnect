Converting between Giotto and other ecosystems with mappings, not converters

GiottoConnect now converts Seurat and Giotto objects with one engine driven by small YAML mapping files. This report explains how it works, why it is easier to extend and maintain than per-version converter functions, how it runs for Seurat today, how AnnData and other ecosystems plug in through an adapter, and which weak points remain.

Branch contract-prototype (off dev_connect, not pushed). GiottoClass 0.7.31 · GiottoDisk 0.0.0.8 · SeuratObject 5.4.0 · Seurat 5.5.0 and 6.0.0. All figures come from examples/seurat_comparison/results/.

Summary

The old approach was one hand-written function per ecosystem and per version: seuratToGiottoV4, seuratToGiottoV5, giottoToSeuratV4, giottoToSeuratV5, each copied in both GiottoConnect and GiottoClass. Each function reached into internal slots and called GiottoClass internals, so every upstream change could break it. That happened: the GiottoConnect copy of seuratToGiottoV5 stopped running when GiottoClass renamed an internal setter, and giottoToSeuratV5 now fails on every object we tested.

The new approach separates what goes where from how it is done. A mapping file declares, for one object structure, which source data becomes which Giotto part. One engine reads the object through its package's public accessors, builds each part with the GiottoClass constructors, and checks the result against the source. Seurat-version differences become different mapping files or are absorbed by parameters; other ecosystems add an adapter and their own mapping files to the same engine.

How it works

A conversion is the same sequence for every ecosystem. Only the boxes marked adapter know anything about Seurat; the rest is generic.

  1. Profile. profileObject() walks the object through attributes() and records every node: path, kind, class, shape and cheap role hints such as integer-valued or rows = number of cells. It never loads the source package.
  2. Choose a mapping. findMapping() keeps mappings whose applies_to predicates hold (class, version, e.g. "the default assay is an Assay5"), prefers an exact structural fingerprint, then the more specific mapping, then coverage.
  3. Bind parameters. Names that vary per dataset (assay, layer, FOV, boundary, graph) are found by rule: the default assay, the first integer-valued layer, the boundary of class Segmentation. for_each parts expand into one part per match, e.g. one per reduction.
  4. Prepare parts. Each part reads its source through a whitelisted public accessor (LayerData, Embeddings, GetTissueCoordinates, GiottoClass getters), then applies declarative ops (rename, flip y, cast) or a registered hook.
  5. Build. Parts become Giotto subobjects through the GiottoClass constructors and are assembled with one setGiotto() call. With source = dir the same call writes disk-backable parts to a GiottoDisk project. For Giotto → Seurat the target builder uses SeuratObject constructors instead.
  6. Check. Validation covers the mapping and the result. readbackCheck() reads every part back and compares it with what the mapping prepared; a difference not covered by a declared or recorded loss fails.
  7. Record. Mapping id, version, fingerprint, bound parameters and losses are stored in the object (Giotto history or Seurat misc) and returned by mappingProvenance().

A mapping file

Excerpt from inst/mappings/seurat-assay5.yaml, the mapping used for Xenium, CosMx, MERSCOPE and Atera objects (125 lines in full). Everything that is specific to Seurat's layout lives here, in data, not in R code.

mapping:
  id: seurat-assay5
  status: verified                 # verified | patched-unreviewed | failed | draft
  source:
    ecosystem: seurat
    applies_to:
      package_version: ">= 5.0.0"
      predicates:
        - { path: "assays/{assay}", class: Assay5 }
  fingerprint: "5c74ef5fee3e2b12"   # structure it was verified on

params:                              # dataset-specific names, found by rule
  assay:      { list: Assays, rule: value_of, path: active.assay, where: { class: Assay5 } }
  layer_raw:  { list: Layers, on: "{assay}", rule: first_where, where: { role: [integer_valued, nonneg] } }
  segmentation: { list: Boundaries, on: "{fov}", rule: first_of_class, class: Segmentation, optional: true }

source_nodes:                        # structural path (for checks) + public accessor (for reading)
  counts:    { path: "assays/{assay}/layers/{layer_raw}",
               get: { fn: LayerData, args: { assay: "{assay}", layer: "{layer_raw}" } } }
  centroids: { path: "images/{fov}/boundaries/{centroids}",
               get: { fn: GetTissueCoordinates, on: "images/{fov}/boundaries/{centroids}" } }
  reduction: { path: "reductions/{red}/cell.embeddings", get: { fn: Embeddings, args: { reduction: "{red}" } } }

parts:
  - id: expr_raw
    part: expression
    from: counts
    to: { spat_unit: cell, feat_type: rna, name: raw }
  - id: locs
    part: spatial_locs
    from: centroids
    ops:
      - { op: rename, map: { x: sdimx, y: sdimy, cell: cell_ID } }
      - { op: scale, factor: -1, cols: [sdimy] }       # image y-down → Giotto y-up
    lossy:
      - { kind: estimated, field: units, note: "FOV coordinates carry no unit; assumed micron" }
    alternatives:                                      # used by repair if the FOV is gone
      - id: locs_from_meta          # coordinates kept as meta.data columns
      - id: locs_from_reduction     # coordinates kept as a "spatial" reduction
  - id: "dimred_{red}"
    part: dim_reduction
    from: reduction
    for_each: { list: Reductions, as: red, exclude: "^(spatial|coords?|centroids?|xy)$" }
    to: { spat_unit: cell, feat_type: rna, name: "{red}", method: "{red}" }
  - id: nn
    part: nn_network
    from: nn
    hook: seurat_graph_to_nn        # names it kNN.<reduction>, recovers k and distances from FindNeighbors

lossy:
  - { kind: dropped, path: "assays/{assay}/layers/scale.data", note: "recomputable; no Giotto slot" }

What a mapping can say

  • applies_to: which objects it is for, by structure.
  • params: names found by rule on the profile.
  • source_nodes: where data sits and which accessor reads it.
  • parts: one per target piece, with ops, a hook, for_each or alternatives.
  • lossy: what is dropped, estimated or ambiguous, stated up front.

What it cannot say

  • Arbitrary R code. Ops are a closed list of 10 (select, exclude, rename, transpose, scale, cast, rownames_to_col, set, set_colnames, cast to table).
  • Accessors outside the whitelist (a schema enum).
  • Anything an LLM writes. LLMs only pick among options during repair.

Two independent checks support this. GiottoDisk's own importers on the same raw folders agree: identical Xenium counts and centroids within 0.55 µm, and identical Visium HD locations on all 386 bins. A Seurat → Giotto → Seurat round trip returns the original counts, metadata, coordinates, polygons, reductions and kNN graph. In the other direction, the legacy giottoToSeuratV5 failed on all 7 tested Giotto objects ("Raw count data not found"), including the GiottoData Visium mini; the mapping converted all 7.

Transparency: nothing is lost silently

  • Declared losses in the mapping: dropped, estimated, ambiguous, recovered from parameters.
  • Recorded losses per conversion, e.g. "Xenium_nn built by FindNeighbors.Xenium.pca on pca; k = 19 neighbours".
  • Readback fails on any difference that no loss explains.
  • Validation flags data the mapping does not read (e.g. Xenium control assays) instead of dropping it quietly.
  • Provenance travels with the object: mappingProvenance(g).
  • Readback found real bugs, e.g. kNN networks with NA weights, before any user saw them.

Memory and disk use the same code path: seuratToGiotto(s, source = dir) only attaches a GiottoDisk source, and GiottoClass's backend-aware setters write expression, polygons and networks to disk. Single runs on crops; the full-size and peak-memory benchmark is still to do.

The cost

The engine is larger than any one converter: 2,847 lines of R across profile, schema, mapping choice, engine, validation, readback, repair and the optional LLM step, against about 1,170 lines of legacy Seurat converter code in GiottoConnect's seurat.R (duplicated in GiottoClass). Everything Seurat-specific is now 607 lines of YAML across six mappings, four hooks, a 196-line Seurat target module and two 16-line wrappers. The engine is written once; from the second ecosystem on, each addition is an adapter and YAML rather than another converter of several hundred lines.

Seurat today

Seurat → Giotto

# picks the mapping that fits the object, converts, checks
g  <- seuratToGiotto(s)
gd <- seuratToGiotto(s, source = "project_dir/")  # GiottoDisk

mappingProvenance(g)$mapping     # "seurat-assay5"
mappingProvenance(g)$losses      # declared + recorded
readbackCheck(s, g)              # PASS: 30 MATCH

Giotto → Seurat

# in-memory or GiottoDisk-backed giotto object
s2 <- giottoToSeurat(g)

findMapping(profileObject(g))$mapping   # giotto-seurat5
readbackCheck(g, s2)             # PASS: 27 MATCH

# Seurat -> Giotto -> Seurat returns the original data

A repair produces a new mapping version marked patched-unreviewed; it is accepted only after validation, conversion and a passing readback, and becomes verified only after review.

Other ecosystems through adapters

The schema, the Giotto contract, parameter binding, ops, validation, readback, repair and provenance do not change per ecosystem. What changes is a small adapter: how to open the input, walk its structure, list names, read a node, and optionally stream large data straight into GiottoDisk.

Sketch: an AnnData mapping

Illustrative only; names are not final. It shows that the same vocabulary covers a file-based format with a different layout (cells × features, categorical metadata, graphs in obsp).

mapping:
  id: anndata-spatial
  source: { ecosystem: anndata, class: h5ad, package: GiottoConnect,
            applies_to: { predicates: [ { path: "obsm/{coords}", kind: dense_matrix } ] } }

params:
  layer_raw: { list: Layers, rule: first_where, where: { role: [integer_valued, nonneg] } }   # X or layers/*
  coords:    { list: Obsm, rule: first_where, where: { name_matches: "^spatial$" } }
  graph:     { list: Obsp, rule: name_is, value: distances, optional: true }

source_nodes:
  counts: { path: "{layer_raw}",   get: { fn: h5adMatrix } }        # streams via GiottoDisk::h5adInput() on disk
  obs:    { path: "obs",           get: { fn: h5adFrame } }         # categoricals decoded, incl. anndata < 0.8
  locs:   { path: "obsm/{coords}", get: { fn: h5adObsm } }
  emb:    { path: "obsm/{red}",    get: { fn: h5adObsm } }
  nn:     { path: "obsp/{graph}",  get: { fn: h5adGraph } }

parts:
  - { id: expr_raw, part: expression, from: counts,
      ops: [ { op: transpose } ],                         # cells x genes → genes x cells
      to: { spat_unit: cell, feat_type: rna, name: raw } }
  - { id: locs, part: spatial_locs, from: locs,
      ops: [ { op: cast, to: table }, { op: set_colnames, cols: [sdimx, sdimy] } ],
      to: { spat_unit: cell, name: raw } }
  - { id: "dimred_{red}", part: dim_reduction, from: emb,
      for_each: { list: Obsm, as: red, where: { name_matches: "^X_" } },
      to: { spat_unit: cell, feat_type: rna, name: "{red}", method: "{red}" } }
  - { id: nn, part: nn_network, from: nn, hook: anndata_graph_to_nn, optional: true,
      to: { spat_unit: cell, feat_type: rna, nn_type: kNN, name: "{graph}" } }

AnnData even improves on Seurat in one place: obsp/distances stores real neighbour distances, so no recovery step is needed. The GiottoDisk h5ad readers merged in PR #97 provide the reading and streaming pieces; the temporary importH5adDisk() layer goes away once anndataToGiotto() runs on the engine.
